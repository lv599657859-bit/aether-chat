# 隐藏上下文引擎

> 你的要求：**能够自行解决上下文问题，但不会显示在明面上，存在很隐私的设置里能看到。**

这句话拆开是三个要求，而且互相拉扯：

1. 上下文必须真的被管理（不是靠模型硬扛长对话）
2. 管理过程必须不可见（说了就出戏）
3. 管理结果必须可核查（否则出了问题你无从下手）

设计上是这样同时满足的。

## 一、真的在管：七层上下文结构

每一轮推理前，`ContextEngine.workingSet(...)` 会重新组装七层：

| 层 | 预算 | 内容 | 是否可裁 |
|---|---|---|---|
| 1 人格 | 900 | soul + 口癖 + 禁忌 + 复刻约束 | 永不裁 |
| 2 canon | — | 铁律（全量）+ 按话题检索的事实 | 铁律不裁 |
| 3 记忆 | 700 | 向量 × 显著度 × 时近性 top-k | 可裁 |
| 4 关系 | 200 | 五维数值 → 语气指令 | 可裁 |
| 5 演出 | 300 | 动作白名单 + 情绪输出格式 | 可裁 |
| 6 守门 | 100 | 沉浸禁令 | 可裁 |
| 7 连续性 | 1400 | 滚动摘要 + 原文窗口 | 按需滑窗 |

`ContextBudget` 有三档预设：`.compact`（2400）/ `.standard`（3600）/ `.roomy`（8000）。
调试期用 roomy 看效果，上线用 standard 省钱。

### 原文窗口怎么滑

```swift
private func trimHistory(_ history: [Message], digest: ConversationDigest?, budget: Int) -> [Message] {
    var usable = history
    // 摘要覆盖点之前的，不再注入 —— 它们已经被压进摘要了
    if let covered = digest?.coveredUpToMessageID,
       let idx = usable.firstIndex(where: { $0.id == covered }) {
        usable = Array(usable.dropFirst(idx + 1))
    }
    // 从最新往回装，装满为止
    var total = 0
    var kept: [Message] = []
    for message in usable.reversed() {
        let cost = TokenEstimator.estimate(renderForModel(message)) + 4
        if total + cost > budget { break }
        total += cost
        kept.append(message)
    }
    return kept.reversed()
}
```

关键点是**「摘要覆盖点」这个游标**。没有它就会犯经典错误：
摘要说了一遍，原文又说了一遍，模型被同一件事灌两次，回复开始复读。

### 记忆的检索不是纯语义

```swift
let score = semantic * 0.55 + item.salience * 0.30 + recency * 0.15
```

只有语义相似，会捞出一堆"相关但不重要"的东西。
加上显著度（约定、秘密权重高）和时近性（最近提到的更可能还在话题里），
才像人脑那种「你一说累，我就想起你上次也是这个点说累」。

记忆还会随时间衰减：

```swift
mutating func decay(now: Date = Date()) {
    let days = max(0, now.timeIntervalSince(lastAccessAt) / 86_400)
    salience = max(0.05, salience * pow(0.995, days))
}
```

**会忘，才像真的。** 一百条全都记着，回答会变成数据库查询。

### 记忆从哪来

每轮对话之后，`MemoryExtractor` 在后台跑一次：

- 有模型：让模型按六类（事实/偏好/事件/感受/约定/私密）抽 JSON，最多 4 条，
  还给每条写一句**她自己的主观注解**（`annotation`）—— 让记忆带上颜色
- 没模型：正则兜底（「我叫…」「我不吃…」「其实我…」「别告诉…」）

注意抽取失败的降级路径：**不会因为模型挂了就不长记性**。

## 二、看不见：物理隔离，而非自觉

隐藏信息的容器是 `Message.hidden`：

```swift
struct HiddenTrace: Codable, Hashable, Sendable {
    var recalledMemoryIDs: [UUID] = []   // 这轮用了哪些记忆
    var canonFactIDs: [UUID] = []        // 这轮用了哪些原作设定
    var innerMonologue: String?          // 内心独白
    var promptTokens: Int = 0            // 上下文占用
    var providerID: String = ""
    var modelID: String = ""
    var notes: [String] = []             // 组装日志
    var oocBlocks: Int = 0               // 出戏拦截次数
    var durationMS: Int = 0
}
```

`MessageBubble`（聊天界面）**只读 `text` / `kind` / `attachments` / `cues` / `emotion`**，
从来不碰 `hidden`。这不是靠开发者自觉 —— 是 `MessageBubble` 的渲染路径里
根本没有引用这个字段的地方。

同样地，界面上的技术文案被替换掉：

| 真实状态 | 界面显示 |
|---|---|
| 正在生成 | 「正在斟酌…」「写了又删…」「似乎在想措辞…」 |
| 请求失败 | 「消息没送到」 |
| 重新生成 | 「让她再说一次」 |

见 `ImmersionGuard.characterful(_:personaName:)` 和 `typingPhrase(seed:tempo:)`。

### 出方向也要守

模型偶尔会漏出元语言：「作为一个 AI，我无法真正感受疲劳。」

`ImmersionGuard.scrub` 会按句切分，**整句删除**（而不是替换成别的话 —— 换了更出戏），
并计入 `oocBlocks`。如果整条都被擦了，兜一句：

> ……（她沉默了一下，像是不太想接这句话）

拦截模式在 `ImmersionGuard.metaPatterns`，可以直接加。

## 三、看得见：潜意识层

入口是暗的：

- 聊天界面连点标题 5 次
- 设置页长按版本号 3 秒

然后面容 ID（`Vault.unlock`，可关）。

进去有六个页签：

| 页签 | 你能看到什么 |
|---|---|
| **概览** | 角色数 / 会话数 / 消息数 / 记忆数 / 关系边数 + 当前引擎 |
| **记忆** | 每一条长期记忆：类型、重要度、唤起次数、她的主观注解、创建时间。左滑可让她忘掉 |
| **上下文** | 每个会话的摘要与未完结线；最近的内心独白；**上下文透视** |
| **关系** | 她对你的五维数值条形图；他们彼此之间的关系；里程碑 |
| **幕间** | 你不看的时候，他们之间发生的对话原文 |
| **开关** | 上下文开关、压缩阈值、检索条数、沉浸守门、自主性 |

### 上下文透视 —— 这个面板最有用的一颗按钮

它会把「此刻模型实际会收到什么」**原样组装并打印出来**：

```
── SYSTEM ──
你叫 青。……
【与原作一致的事实（不得违背）】
- [外貌] 银发红瞳：…
【你记得的事】
- (偏好) 我不吃香菜
【你和说话人的关系】目前是「朋友」…
【演出协议】…
【绝对禁令】…

── USER ──
我今天有点累

── 估算 ──
约 2874 tokens
```

下面是组装日志（`WorkingSet.notes`）：

```
人格层锚定，指纹 a3f91c02
canon 命中 6 条
唤起记忆 4 条
注入摘要，覆盖至 7b2e1a04
原文窗口 18 条
预算占用 ~2874/3600 tokens
```

**为什么这个按钮必须存在**：上下文引擎出问题时，症状永远是"她变笨了"
或者"她忘了刚才说过的话"—— 你没法从外部区分是检索挂了、摘要错了、
还是窗口滑过头了。透视一下，五秒钟定位。

## 测试

`Tests/ContextEngineTests.swift`：

- `testSystemPromptAlwaysAnchorsPersona` —— 人格每轮重锚 + 守门默认开启
- `testRelevantMemoryOutranksIrrelevant` —— 相关记忆赢过噪音

- `testTokenEstimatorHandlesCJK` —— 中文 token 估算合理

## 一个诚实的限制

现在用的是**固定预算分配**，不是动态规划。极端情况下（比如一屏塞了
二十张图的消息）可能会出现某层被挤空。真上线之后应该在 `ContextBudget`
之上加一层「按当前轮的实际需求动态调档」，这个留给你。
